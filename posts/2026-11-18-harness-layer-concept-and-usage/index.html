Notes · 2026.11.18

모델은 엔진, 하네스는 핸들: Harness Layer 이해하기

LLM은 다음 토큰을 예측하는 엔진이고, 그 엔진이 실제 작업을 하도록 감싸는 것이 하네스 계층입니다. Rules·Skills·Hooks·MCP 네 축의 역할과 실전 용도, Cline의 전역·프로젝트 구조, 커뮤니티 스킬을 얹기 전에 점검할 것까지 정리했습니다.

Notes 2026년 11월 18일 5분 읽기 #harness#cline#ai-agent#llm#rules#hooks#notes

같은 모델을 쓰는데 결과가 다를 때가 있습니다. 어떤 날은 에이전트가 알아서 테스트까지 돌리고 깔끔하게 끝내고, 어떤 날은 같은 실수를 세 번 반복합니다. 모델을 바꾸지 않았는데도 그렇습니다. 이 차이를 만드는 것이 이 글의 주제인 하네스 계층(Harness Layer) 입니다.

AI 코딩 도구를 처음 만지면 모델 이름부터 봅니다. Claude인지, GPT인지, Qwen인지. 물론 중요합니다. 그런데 실무에서 결과를 가르는 것은 그 위에 얹힌 얇은 층입니다. 무엇을 프롬프트에 넣고, 어떤 도구를 허용하고, 어떤 명령을 막고, 어떤 절차를 준비해 두었는가. 이 글은 그 층이 무엇으로 이루어지고 어디에 쓰이는지를 개념과 용도 중심으로 정리한 노트입니다. 설치 명령보다 "왜 필요한가"에 집중합니다.

모델만으로는 부족한 이유

LLM이 하는 일은 하나입니다. 앞에 주어진 문맥을 보고 다음에 올 토큰의 확률을 계산합니다. 이 정의를 끝까지 밀고 가면, 모델에게 없는 것이 몇 가지 보입니다.

  • 기억이 없습니다. 대화가 끝나면 아무것도 남지 않습니다. 어제 정한 규칙을 오늘 다시 알려 주지 않으면 모델은 모릅니다.
  • 실행 권한이 없습니다. 모델은 파일을 직접 쓰지 못합니다. "이 파일을 고쳐라"라는 텍스트를 뱉을 뿐이고, 실제로 고치는 것은 모델 바깥의 프로그램입니다.
  • 자기 출력을 검증하지 않습니다. 코드가 컴파일되는지, 테스트가 통과하는지는 돌려 봐야 압니다. 모델의 확신과 정확성은 별개입니다.
  • 일관성이 없습니다. 같은 요청에도 샘플링에 따라 조금씩 다르게 답합니다. 팀 컨벤션을 매번 같은 방식으로 지키게 만들려면 외부 장치가 필요합니다.

여기서 흔한 오해가 하나 있습니다. 프롬프트를 잘 쓰면 이 문제가 해결된다는 생각입니다. 프롬프트는 부탁입니다. 모델은 대체로 들어주지만, 반드시 들어주지는 않습니다. 반면에 하네스는 장치입니다. 도구 호출 직전에 스크립트가 돌고, 종료 코드가 0이 아니면 실행이 취소됩니다. 부탁과 장치의 차이가 결과의 재현성을 만듭니다.

그래서 하네스를 이렇게 정의해 두겠습니다. 모델 가중치 바깥에서, 모델에 들어가는 것과 모델이 하는 일을 통제하는 모든 층. 프롬프트에 실리는 규칙, 불러올 수 있는 절차, 실행 전후의 검사, 연결된 도구, 그리고 그 결과가 다시 문맥으로 돌아오는 루프까지 포함합니다. 자동차에 비유하면 모델은 엔진이고, 하네스는 핸들과 브레이크와 계기판입니다. 엔진 출력이 세다고 목적지에 안전하게 도착하지는 않습니다.

하네스를 이루는 네 가지 축

하네스는 거창한 제품이 아닙니다. 대개 다음 네 가지가 전부이고, 여기에 문맥을 관리하는 루프가 붙습니다. 각 축은 "모델에게 언제 무엇이 보이는가"가 다릅니다.

Rules — 항상 켜져 있는 규약

규칙은 모든 요청에 함께 실리는 짧은 지침입니다. 모델이 매번 물어보지 않아도 알았으면 하는 것들을 적습니다. 팀의 네이밍 규칙, 폴더 구조, 에러 처리 방식, "이 경로는 건드리지 말 것" 같은 금지선입니다.

Cline은 규칙을 여러 위치에서 읽습니다. 프로젝트에는 .clinerules/ 또는 .cline/rules/ 폴더를 두고, 전역에는 ~/Documents/Cline/Rules(macOS·Linux) 또는 ~/.cline/rules를 씁니다. 다른 도구와 호환되는 AGENTS.md도 함께 인식합니다. 규칙 파일은 보통 관심사마다 하나씩 나눕니다.

<!-- .clinerules/coding.md -->
# 코드 규칙
- TypeScript의 strict 모드를 끄지 않습니다.
- 외부 API 호출은 반드시 src/lib/http.ts를 거칩니다.
- legacy/ 폴더는 읽기만 하고 수정하지 않습니다.
- 커밋 메시지는 feat:, fix:, docs: 접두사를 씁니다.

규칙의 강점은 단순함이고, 약점도 단순함입니다. 항상 문맥에 실리기 때문에 길어질수록 비용이 커지고, 반대로 짧게 쓰면 예외 상황을 담지 못합니다. Cline은 이 문제를 조건부 규칙으로 완화합니다. 규칙 파일 맨 위에 frontmatter로 경로 패턴을 적으면, 그 경로의 파일을 만질 때만 규칙이 활성화됩니다.

---
paths:
  - "src/components/**"
---

# 컴포넌트 규칙
- 컴포넌트는 함수형으로 작성하고 default export를 쓰지 않습니다.
- 스타일은 Tailwind 클래스만 사용합니다.

문서 스타일 규칙이 애플리케이션 코드를 고칠 때까지 문맥을 차지하지 않는다는 점이 핵심입니다. 규칙 패널에서 파일마다 켜고 끌 수 있으므로, 실험 중에는 엄격한 테스트 규칙을 잠시 내려 둘 수도 있습니다.

Skills — 필요할 때만 꺼내는 절차서

규칙이 "무엇을 지킬까"라면 스킬은 "어떤 순서로 할까"입니다. 배포, 마이그레이션, 릴리스 노트 작성처럼 단계가 여러 개이고 자주 바뀌는 작업은 규칙에 넣기에는 너무 깁니다. 스킬은 이런 절차를 SKILL.md 한 파일에 담아 두고, 관련된 요청이 들어올 때만 불러옵니다.

---
name: release-check
description: 릴리스를 준비할 때 사용합니다. 버전 올리기, 체인지로그 작성,
  테스트 실행, 태그 생성 순서를 안내합니다.
---

# 릴리스 점검

1. `package.json`의 버전을 올리고 커밋합니다.
2. `CHANGELOG.md`에 이번 변경을 "변경/수정/제거"로 나눠 적습니다.
3. `npm ci && npm test`를 실행합니다. 실패하면 여기서 멈춥니다.
4. `git tag v<버전>` 후 push하고, 릴리스 노트에 테스트 결과를 붙입니다.

동작 방식이 흥미롭습니다. Cline은 시작할 때 모든 스킬의 name과 description만 읽습니다. 스킬 하나당 약 100토큰 수준입니다. 요청이 설명과 맞으면 그때 SKILL.md 본문을 읽어 오고, 본문은 5,000토큰 이하로 유지하는 것이 권장됩니다. 그러니 스킬을 열 개 설치해도 열 개의 본문이 항상 문맥을 차지하지는 않습니다. 대신 설명이 부실하면 엉뚱한 순간에 불리거나 아예 불리지 않습니다. description은 "무엇을 하는지"보다 "언제 쓰는지"를 적는 편이 잘 걸립니다.

채팅창에서 /를 눌러 스킬을 직접 호출할 수도 있습니다. 자동 매칭을 기다리지 않고 특정 절차를 강제하고 싶을 때 씁니다.

Hooks — 실행 전후에 끼어드는 자동 장치

훅은 모델의 판단을 거치지 않습니다. 정해진 지점에서 프로그램이 먼저 돕니다. 이 점이 규칙과 결정적으로 다릅니다. 규칙은 모델이 읽고 따르기를 기대하지만, 훅은 모델이 무엇을 결정했든 상관없이 실행을 가로챕니다.

가장 널리 쓰이는 이름이 PreToolUse와 PostToolUse입니다. 도구가 실행되기 직전과 직후입니다. Claude Code는 이 이름으로 훅 이벤트를 제공하고, 훅 스크립트는 표준 입력으로 tool_name, tool_input 같은 JSON을 받습니다. 종료 코드 2로 끝나면 그 도구 호출은 취소되고, 표준 오류에 쓴 이유가 모델에게 피드백으로 전달됩니다. 설정은 이런 모양입니다.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "./scripts/guard-env.sh" }
        ]
      }
    ]
  }
}

guard-env.sh는 하는 일이 단순합니다. 입력에서 파일 경로를 꺼내 .env나 secrets/가 걸리면 이유를 출력하고 종료 코드 2로 끝냅니다. 모델은 "환경 변수 파일은 직접 수정할 수 없습니다"라는 피드백을 받고 다른 방법을 찾습니다. 사람이 매번 말릴 필요가 없습니다.

Cline에서는 도구 호출 전후 개입을 SDK·CLI 플러그인의 생명주기 훅(beforeTool, afterTool)으로 구현합니다. 위치만 보면 ~/.cline/hooks/와 프로젝트의 .cline/hooks/ 디렉터리도 함께 읽습니다. 도구마다 다른 에이전트가 다른 형식을 쓰지만, "실행 직전에 검사하고, 실행 직후에 결과를 확인한다"는 지점 자체는 거의 같습니다.

훅에서 꼭 기억할 점이 있습니다. 훅은 그 도구 호출을 막을 뿐입니다. 같은 파일을 다른 경로로 건드리는 명령은 통과할 수 있습니다. 그래서 훅 하나로 끝내지 않고, 권한 설정(permissions.deny)이나 샌드박스와 겹쳐 둡니다. 하네스는 한 겹이 아니라 여러 겹으로 만들 때 쓸만해집니다.

MCP / Tools — 모델의 손발

모델이 세상에 영향을 주는 방법은 도구뿐입니다. 파일 읽기·쓰기, 터미널 실행, 검색 같은 기본 도구가 있고, MCP(Model Context Protocol)는 여기에 외부 서비스를 붙이는 표준 통로입니다. 이슈 트래커, 문서 저장소, 사내 API, 데이터베이스 조회를 같은 대화 안에서 호출할 수 있게 됩니다.

Cline CLI에서는 MCP 서버를 ~/.cline/data/settings/cline_mcp_settings.json에 등록하고, cline mcp 마법사나 cline mcp add로 추가합니다. 로컬 서버는 command와 args로, 원격 서버는 url로 붙습니다.

도구는 능력이 아니라 통로라는 점이 중요합니다. 통로를 열어 두면 편해지지만, 열어 둔 만큼 사고의 표면적도 넓어집니다. 그래서 하네스는 어떤 도구를 자동으로 실행하고 어떤 도구는 사람의 승인을 받을지 정합니다. 읽기는 자동, 쓰기와 삭제는 승인, 배포는 아예 금지하는 식입니다.

그리고 Context 루프

네 축이 한 바퀴를 돕니다. 요청이 들어오면 규칙과 관련 스킬이 실리고, 모델이 도구를 고르고, 훅이 검사하고, 실행 결과가 다시 문맥으로 돌아옵니다. 모델은 이 루프를 돌면서 자기 출력을 조금씩 고칩니다.

문제는 문맥이 유한하다는 것입니다. 대화가 길어지면 앞부분이 요약되거나 잘립니다. 그때 가장 먼저 사라지는 것이 대개 초반에 넣은 규칙입니다. 그래서 긴 세션에서 규칙을 잊는 것은 모델의 성실성 문제가 아니라, 매 턴 다시 넣어 주는 장치가 없기 때문입니다. 압축 직후에 핵심 규칙을 다시 주입하는 훅(SessionStart의 compact 시점)이 이런 이유로 쓰입니다.

네 축을 한 표로 정리하면 이렇습니다.

축 언제 문맥에 들어오나 무엇을 담나 없으면
Rules 항상 지킬 것, 금지선 매번 다시 설명해야 함
Skills 관련 요청이 올 때 여러 단계의 절차 긴 절차를 즉석에서 즉흥으로
Hooks 도구 실행 전후 검사, 차단, 재검증 실수를 사후에 사람이 발견
MCP · Tools 모델이 호출할 때 외부 세계로 나가는 통로 읽고 고칠 수 있는 범위가 좁음

실제로 어디에 쓰나요

개념은 이 정도면 충분합니다. 실제로는 네 가지 상황에서 가장 자주 쓰게 됩니다.

1. 팀 코드 스타일 유지. 신입이든 에이전트든 같은 규칙으로 일하게 만드는 일입니다. 네이밍, 폴더 구조, 에러 처리, 커밋 메시지 형식을 규칙에 적고 레포에 커밋합니다. 파일 종류별로 조건부 규칙을 걸면 문서 규칙이 코드를 고칠 때 끼어들지 않습니다. 효과는 조용합니다. 리뷰에서 "이거 우리 컨벤션 아니에요"라는 코멘트가 줄어듭니다.

2. 위험 작업 차단. .env 수정, 프로덕션 DB 접속, rm -rf, 강제 push. 한 번의 사고로 되돌릴 수 없는 것들입니다. 규칙에 "하지 마세요"라고 적는 것과, 실행 직전에 막는 것은 다릅니다. 전자는 부탁이고 후자는 장치입니다. 여기에 도구 권한 설정을 겹쳐 두면 "규칙도 있고, 훅도 있고, 권한도 없다"는 삼중 방어가 됩니다.

3. 빌드·테스트 자가 재검증. 파일을 고친 직후 테스트를 돌리고, 실패 로그를 모델에게 되돌려 주는 루프입니다. 사람이 "테스트 돌려 봐"라고 말하지 않아도 모델이 스스로 고칩니다. 조건은 하나입니다. 테스트가 빨라야 합니다. 10분짜리 테스트를 매 수정마다 돌리면 루프가 아니라 정지입니다. 관련 테스트만 골라 돌리는 스킬을 함께 두는 이유입니다.

4. 외부 도구 연동. 이슈 트래커에서 티켓을 읽고, 문서를 참고하고, 사내 API를 호출하는 일입니다. MCP 서버를 붙이면 대화를 떠나지 않고 처리됩니다. 다만 어떤 서버에 어떤 권한을 줬는지 목록을 관리해야 합니다. 토큰은 프롬프트가 아니라 MCP 설정의 환경 변수로 넣습니다.

Cline에서의 하네스 구조

도구마다 폴더 이름은 달라도 구조는 비슷합니다. Cline을 기준으로 보면 하네스는 두 곳에 나뉘어 있습니다.

  • 전역 ~/.cline/ — 내 모든 프로젝트에 적용됩니다. rules/, skills/, hooks/, workflows/, agents/, plugins/가 있고, API 키와 MCP 설정은 ~/.cline/data/settings/ 아래에 있습니다. 개인 취향과 개인 안전장치를 두는 곳입니다.
  • 프로젝트 .cline/ — 그 레포에서만 적용됩니다. 같은 하위 폴더 구조에 AGENTS.md(레포 루트)와 기존 .clinerules/도 함께 읽힙니다. 팀이 함께 지킬 것을 두고 레포에 커밋합니다.

둘이 충돌하면 워크스페이스 규칙이 우선합니다. 전역은 기본값이고, 레포는 그 프로젝트의 답이라는 뜻입니다. 그래서 판단 기준도 단순합니다. 혼자 쓰는 취향이면 전역, 팀이 같은 방식으로 일해야 하면 레포. 커밋 메시지 형식은 취향일 수도 있고 팀 규칙일 수도 있지만, 배포 절차와 건드리면 안 되는 경로는 언제나 레포에 둡니다.

한 가지 주의할 점이 있습니다. .cline/에는 규칙과 스킬처럼 공유해도 되는 것만 커밋합니다. ~/.cline/data/settings/providers.json에는 API 키가 들어가므로 절대 레포로 가져오지 않습니다. 시크릿은 환경 변수로 두고, 설정 파일에는 이름만 남깁니다.

생각해 보기: 설치보다 먼저 정할 것

여기까지 읽으면 자연스럽게 다음 질문이 옵니다. "그래서 좋은 스킬 어디서 받나요?" 커뮤니티 스킬을 얹는 명령은 이미 있습니다.

npx skills add https://github.com/cline/skills

cline/skills 저장소에는 Cline이 쓰는 스킬들이 공개되어 있습니다. 코드 리뷰를 여러 관점의 하위 에이전트로 나눠 돌리는 review-team, Cline SDK로 에이전트를 만드는 cline-sdk, Linear를 터미널에서 다루는 linear-sdk-scripting 같은 것들입니다. npx skills는 Agent Skills 표준을 따르는 스킬을 각 에이전트의 스킬 폴더로 가져다 놓는 도구라서, Cline뿐 아니라 Claude Code나 Cursor에서도 같은 명령으로 쓸 수 있습니다.

명령은 한 줄이지만, 이 한 줄을 치기 전에 생각해 볼 것이 남습니다. 설치 자체는 싸고, 유지비는 문맥과 신뢰이기 때문입니다.

  • 내 프로젝트에 정말 필요한 규칙과 위험 차단 훅은 무엇인가? 스킬 열 개보다, .env를 막는 훅 하나와 커밋 규칙 세 줄이 먼저입니다. 하네스는 많이 갖출수록 좋아지는 물건이 아닙니다. 지금 아픈 곳에 맞춰야 합니다.
  • 전역에 둘 것과 레포에 커밋할 것의 경계는 어디인가? 이 경계를 정하지 않으면 팀원은 서로 다른 하네스로 일하고, 리뷰에서 그 차이가 드러납니다. "이건 내 취향인가, 팀의 약속인가"를 기준으로 나눠 보시면 대개 답이 나옵니다.
  • 스킬이 늘어나면 설명이 겹치지 않는가? 설명이 비슷한 스킬이 둘이면 엉뚱한 쪽이 불립니다. 스킬을 추가할 때마다 "이 요청에 어느 스킬이 걸려야 하는가"를 한 번씩 확인하는 편이 좋습니다.
  • 하네스가 막지 못하는 것은 무엇인가? 훅은 도구 호출을 막지만, 같은 일을 하는 다른 경로까지 막지는 못합니다. 권한과 샌드박스가 어디까지 책임지는지 알고 있어야 합니다.
  • 남의 스킬은 검토했는가? 스킬 본문은 내 에이전트가 따를 지시문입니다. 코드를 리뷰하듯 읽고 넣는 것이 맞습니다. npx로 받는 파일도 마찬가지입니다.

이 질문들에 답이 생기면 설치 순서도 자연스럽게 정해집니다. 다음 편에서는 npx로 실제 스킬을 얹고, 전역과 레포의 경계를 정하고, 위험 작업을 막는 훅 하나를 직접 걸어 보는 실습을 정리하겠습니다.

마무리

하네스는 모델을 똑똑하게 만드는 장치가 아닙니다. 모델이 실수해도 크게 다치지 않게 만드는 장치입니다. 그 사실을 받아들이면 설계가 쉬워집니다. 잘하는 일은 모델에게 맡기고, 지켜야 하는 것은 장치로 옮깁니다.

오늘 해 볼 일은 하나면 충분합니다. 지금 작업 중인 레포에 규칙 파일 하나를 만들고, 이번 주에 한 번이라도 아팠던 실수를 세 줄로 적어 보는 것. 그 세 줄이 하네스의 첫 겹입니다.
