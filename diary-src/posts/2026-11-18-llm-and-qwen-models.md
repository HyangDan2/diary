지난 글에서 모델은 엔진, 하네스는 핸들이라고 적었습니다. 그 글은 핸들 쪽 이야기였습니다. 규칙을 어떻게 넣고, 도구 실행을 어디서 막고, 절차를 어떻게 꺼내는가 하는 문제였습니다.

이번 글은 엔진을 열어 봅니다. LLM이 실제로 무엇을 계산하는지, 그 계산이 어떻게 "쓸 만한 능력"이 되는지, 그리고 요즘 자주 보이는 Qwen 모델 이름들이 무엇을 뜻하는지 정리합니다. 하네스 편을 먼저 읽지 않아도 읽히도록 썼지만, 두 글은 한 쌍입니다. [모델은 엔진, 하네스는 핸들](/diary/posts/2026-11-18-harness-layer-concept-and-usage/)에서 이어집니다.

## LLM이 무엇이고 어떻게 동작할까

한 문장으로 줄이면 이렇습니다. **LLM은 앞에 주어진 토큰 열을 받아, 다음에 올 토큰의 확률분포를 계산하는 함수입니다.** 그 이상도 그 이하도 아닙니다. 놀라운 능력은 이 단순한 계산을 아주 큰 신경망과 아주 많은 데이터로 반복한 결과입니다.

### 다음 토큰 예측 — 한 번에 한 글자씩

텍스트는 먼저 토큰으로 쪼개집니다. 토큰은 단어보다 작고 글자보다 큰 단위입니다. "날씨는"이 한 토큰일 수도 있고, "날"과 "씨는"으로 나뉠 수도 있습니다. Qwen3.5·3.8 계열은 어휘가 248,320개쯤 됩니다. 모델의 출력은 이 어휘 전체에 대한 점수(logit)이고, softmax를 거치면 합이 1인 확률분포가 됩니다.

문맥이 "오늘 창원 날씨는"이라면 다음 토큰의 확률은 대략 이렇게 나옵니다. (아래 숫자는 설명을 위한 예시입니다.)

- `맑` 42%, `흐` 23%, `비` 16%, `구` 9%, 나머지 10%

여기서 하나를 고릅니다. 고르는 규칙이 샘플링입니다. **temperature**는 분포의 뾰족함을 조절합니다. 낮추면 1등에 몰리고, 높이면 꼬리도 뽑힙니다. **top-p**는 누적 확률이 p가 되는 지점까지만 남기고 자릅니다. **top-k**는 상위 k개만 남깁니다. 셋 다 "무엇을 후보로 둘 것인가"를 정하는 손잡이입니다.

고른 토큰은 문맥 끝에 붙습니다. 그리고 같은 계산을 다시 합니다. "맑"이 붙으면 다음에는 "음"이나 "겠"이 높아집니다. 이렇게 자기 출력을 입력으로 되먹이는 구조를 **autoregressive**라고 부릅니다. 300토큰짜리 답은 300번의 계산입니다.

여기서 실무에 바로 쓰이는 사실이 두 개 나옵니다.

1. **같은 질문에도 답이 달라집니다.** 확률에서 뽑기 때문입니다. 재현성이 필요하면 temperature를 0에 가깝게 두고, 그렇다고 완전히 같아지지는 않습니다. 배치 구성과 커널에 따라 미세하게 흔들립니다.
2. **답이 길수록 느리고 비쌉니다.** 토큰 수가 곧 계산 횟수이고 청구 단위입니다. "짧게 답해 줘"가 미학이 아니라 비용 문제인 이유입니다.

### 그 능력은 어디서 오나 — 학습 3단계

같은 다음 토큰 예측인데, 무엇을 정답으로 주느냐에 따라 단계가 나뉩니다.

| 단계 | 데이터 | 목표 | 결과물 |
| --- | --- | --- | --- |
| Pre-training | 웹·코드·PDF 등 수조 토큰 | 다음 토큰 맞히기 | Base 모델 (지시를 모름) |
| SFT | 사람이 쓴 지시-답 쌍 | 대화 형식과 말투 | Instruct 모델 |
| RL | 검증 가능한 정답, 사람 선호 | 더 자주 맞히기 | 추론·정렬된 모델 |

**Pre-training**은 압축에 가깝습니다. 수조 토큰의 다음 토큰을 맞히려면 문법, 상식, 코드의 규칙, 번역 대응이 가중치 안에 들어와야 합니다. Qwen2.5가 18조 토큰, Qwen3가 약 36조 토큰으로 학습됐다는 발표가 나온 배경입니다. 이 단계의 결과물(base model)은 다음 토큰은 잘 맞히지만 "질문에 답하라"는 지시는 모릅니다. 문서 이어 쓰기 기계에 가깝습니다.

**SFT**(Supervised Fine-Tuning)는 형식을 가르칩니다. 지시와 모범 답을 쌍으로 주고, 채팅 템플릿에 맞춰 답하게 합니다. system/user/assistant 역할 구분, 거절하는 말투, 목록 만드는 습관이 여기서 생깁니다. 우리가 API로 만나는 "Instruct" 모델이 이 단계의 결과물입니다.

**RL**은 목표를 바꿉니다. SFT는 "모범 답과 비슷하게"를 가르치지만, RL은 "맞히면 보상"을 줍니다. 수학 문제의 정답, 코드의 테스트 통과, 사람의 선호 투표가 보상이 됩니다. 검증 가능한 보상(RLVR)이 특히 강력한 이유는, 모델이 사람이 쓴 풀이보다 나은 풀이를 스스로 찾아낼 수 있기 때문입니다. 요즘 모델이 답하기 전에 길게 생각하는 습관도 이 단계에서 나옵니다. 생각을 길게 하는 쪽이 보상을 더 받으면 그쪽으로 학습됩니다.

Qwen3.5 발표문은 이 RL을 "백만 단위 에이전트 환경"까지 확장했다고 적습니다. 사람이 정답을 다 써 줄 수 없는 에이전트 작업에서는, 환경이 주는 성공·실패 신호가 보상이 됩니다.

### 도구 호출 — 모델은 실행하지 않습니다

LLM의 출력은 언제나 텍스트입니다. 파일을 쓰지도, 명령을 돌리지도 못합니다. 도구 호출(tool calling)은 이 한계를 우회하는 약속입니다.

먼저 도구 목록을 요청에 함께 넣습니다. 이름, 설명, 인자의 JSON Schema입니다.

```json
{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "도시의 현재 날씨를 조회합니다. 날씨·기온·강수 질문에 사용하세요.",
    "parameters": {
      "type": "object",
      "properties": {
        "location": { "type": "string", "description": "도시 이름. 예: 창원" }
      },
      "required": ["location"]
    }
  }
}
```

모델은 답 대신 도구 호출을 뱉습니다. "get_weather를 location=창원으로 불러라"라는 텍스트입니다. 그러면 바깥 프로그램이 실제로 API를 호출하고, 결과를 `role: tool` 메시지로 문맥에 다시 넣습니다. 모델은 그 결과를 읽고 답을 마저 씁니다.

```python
messages = [
    {"role": "system", "content": "너는 날씨 도우미다. 도구 결과에 없는 값은 추측하지 않는다."},
    {"role": "user", "content": "오늘 창원 날씨 어때?"},
]

# 1) 모델이 도구를 고른다
res = client.chat.completions.create(model="Qwen/Qwen3.8-27B", messages=messages, tools=tools)
call = res.choices[0].message.tool_calls[0]

# 2) 실행은 내 코드가 한다
result = get_weather(**json.loads(call.function.arguments))

# 3) 결과를 문맥에 넣고 다시 부른다
messages.append(res.choices[0].message)
messages.append({"role": "tool", "tool_call_id": call.id, "content": json.dumps(result, ensure_ascii=False)})
final = client.chat.completions.create(model="Qwen/Qwen3.8-27B", messages=messages, tools=tools)
```

이 루프에서 기억할 점이 몇 가지 있습니다.

- **도구 설명이 곧 프롬프트입니다.** 모델이 도구를 고르는 근거는 `description`과 인자 설명뿐입니다. "언제 쓰는지"를 적지 않으면 엉뚱한 순간에 불립니다. 하네스 편에서 스킬 설명에 대해 했던 말과 같습니다.
- **병렬 호출은 독립 작업에만.** "베이징과 상하이 날씨"는 한 번에 두 호출로 나갑니다. 앞 호출의 결과가 다음 인자에 필요한 경우에는 순차로 돌려야 합니다.
- **실패도 정상 경로입니다.** 타임아웃, 404, 빈 결과가 그대로 문맥에 들어갑니다. 모델이 다른 도구를 고르거나 인자를 고쳐 다시 부르는 것이 이 구조의 장점이고, 그래서 도구 결과를 "사람이 읽어도 이해되는" 형태로 돌려주는 편이 좋습니다.
- **실행 권한은 모델 밖에 있습니다.** 무엇을 실행할지, 어떤 도구는 승인을 받을지는 하네스가 정합니다. 모델이 아무리 그럴듯하게 호출해도 실행기가 거절하면 아무 일도 일어나지 않습니다.

## Qwen 라인업 한눈에 보기

Qwen은 알리바바의 모델군입니다. 2023년 Tongyi Qianwen에서 시작해 2.5, 3, 3.5, 3.6, 3.8로 이어졌습니다. 이름은 대개 `Qwen<세대>-<크기>`이고, MoE 모델은 뒤에 `-A<활성 파라미터>`가 붙습니다. `Qwen3.5-397B-A17B`는 "3.5세대, 총 397B, 토큰당 17B 활성"으로 읽으면 됩니다.

| 세대 | 시점 | 대표 모델 | 무엇이 바뀌었나 |
| --- | --- | --- | --- |
| Qwen2.5 | 2024-09 | 0.5B~72B dense | 18조 토큰, 최대 128K 문맥, 도구 호출 정착 |
| Qwen3 | 2025-04 | 0.6B~32B, 30B-A3B, 235B-A22B | 36조 토큰, 119개 언어, 하이브리드 씽킹 도입 |
| Qwen3-Next | 2025-09 | 80B-A3B | Gated DeltaNet 선형 어텐션 실험 |
| Qwen3.5 | 2026-02 | 397B-A17B, 122B-A10B, 35B-A3B, 27B | 네이티브 멀티모달, 201개 언어, 3:1 하이브리드 |
| Qwen3.6 | 2026-04 | 35B-A3B, 27B | 안정성·에이전트 코딩, 추론 보존 도입 |
| Qwen3.7 | 2026-05~06 | Max, Plus, VLA | API로만 나온 세대 (오픈 웨이트 미공개) |
| Qwen3.8 | 2026-08 | 2.4T-A95B, 27B | Max급 최초 오픈, 27B는 Apache 2.0 |

Qwen3.7이 눈에 걸립니다. Max와 Plus, VLA가 모두 API로만 나왔고 오픈 웨이트는 없었습니다. 3.8에서 27B가 Apache 2.0으로 다시 풀린 것은, 오픈 모델 사용자 입장에서 한 세대를 건너뛴 셈입니다.

### Dense vs MoE — `총-A활성` 읽는 법

여기서 이름 하나를 뜯어보겠습니다. `Qwen3.5-397B-A17B`.

- **397B는 총 파라미터입니다.** 가중치 전부를 메모리에 올려야 합니다.
- **17B는 토큰 하나를 만들 때 실제로 계산하는 양입니다.** 512개 expert 중 10개와 공용 expert 1개만 켜집니다.

전체의 4.3%만 계산하는 셈입니다. 그러면 왜 이렇게 만드나. 답은 "메모리를 사서 계산을 아끼는" 구조이기 때문입니다. Dense 모델에서 397B급 지식을 얻으려면 토큰마다 397B를 계산해야 합니다. MoE에서는 같은 지식을 메모리에 두고, 토큰마다 필요한 부분만 계산합니다. 대신 GPU 메모리는 총량만큼 필요합니다.

| | Dense | Sparse MoE |
| --- | --- | --- |
| 계산량 | 총 파라미터에 비례 | 활성 파라미터에 비례 |
| 메모리 | 총 파라미터 | 총 파라미터 (전부 상주) |
| 배치 효율 | 예측 가능 | 라우팅에 따라 흔들림 |
| 튜닝 난이도 | 낮음 | 라우터·부하 분산 주의 |
| 예 | Qwen3.8-27B | Qwen3.5-397B-A17B |

MoE의 대가는 학습과 서빙 쪽에 있습니다. expert마다 트래픽이 몰리면 한 GPU만 바빠지고, 배치가 작으면 켜지는 expert가 매번 달라 캐시 효율이 떨어집니다. 그래서 "총 파라미터가 크면 무조건 좋다"가 아니라, 동시성과 메모리 예산을 함께 봐야 합니다.

### 하이브리드 어텐션 — Gated DeltaNet이 끼어든 이유

어텐션은 토큰끼리 서로를 보는 연산입니다. 문제는 문맥이 길어질수록 캐시가 커진다는 것입니다. 표준 어텐션은 과거 토큰의 key/value를 전부 들고 있어야 하므로, KV 캐시가 문맥 길이에 정비례합니다.

**Gated DeltaNet**(GDN)은 이 지점을 바꿉니다. 과거를 전부 저장하는 대신, 고정 크기의 상태를 델타 규칙으로 갱신하고 게이트로 감쇠시킵니다. 상태 크기가 문맥 길이와 무관하므로, 긴 문맥에서도 캐시가 선형으로만 늘지 않습니다. Qwen3-Next가 이 구조를 먼저 시험했고, 3.5에서 본격적으로 규모를 키웠습니다.

다만 선형 어텐션만으로는 부족합니다. 정확히 어딘가에 있던 문장을 그대로 찾아오는 일(검색)에서 약합니다. 그래서 3층은 GDN, 1층은 완전 어텐션으로 섞습니다. 397B-A17B는 이 블록이 15번 반복돼 60층이고, 27B는 16번 반복돼 64층입니다. 27B 기준으로 완전 어텐션은 16층뿐이라, 모든 층이 완전 어텐션이라면 필요했을 KV 캐시의 4분의 1만 씁니다.

숫자로 보면 이렇습니다. 27B가 262,144 토큰을 f16 KV로 들고 있으면 약 16GiB입니다. 64층이 전부 완전 어텐션이었다면 64GiB였을 양입니다. 그래서 "27B인데 24GB 카드에서 128K 문맥이 된다"는 이야기가 나옵니다. 물론 KV를 q8로 줄이고 문맥을 줄이는 조건이 붙습니다.

## 핵심 모델 2종 비교

라인업이 넓어서 실제로는 두 모델 사이에서 고민하게 됩니다. 서버에 두는 397B-A17B와 책상 위에 두는 27B입니다. 스펙을 나열하기보다 "무엇에 쓰는가"를 중심으로 정리했습니다.

### Qwen3.5-397B-A17B — 서버에 두는 397B

2026년 2월 16일에 공개된 3.5세대의 첫 모델입니다. Apache 2.0입니다.

| 항목 | 값 |
| --- | --- |
| 파라미터 | 총 397B · 토큰당 17B 활성 |
| 전문가 | 512개 중 10 routed + 1 shared |
| 층 | 60층 (GDN 3 : Gated Attention 1) |
| 문맥 | 262,144 네이티브, 약 1.01M까지 확장 |
| 입력 | 텍스트·이미지·비디오 네이티브 |
| 언어 | 201개 언어·방언 |
| 라이선스 | Apache 2.0 |

이 모델의 핵심은 세 가지입니다.

**네이티브 멀티모달.** 이미지 인코더를 따로 붙인 구조가 아니라, 텍스트와 이미지 토큰을 처음부터 함께 학습했습니다. 그래서 도표·문서·영상 이해가 부가 기능이 아니라 기본 능력입니다.

**201개 언어.** 3세대의 119개에서 늘었습니다. 어휘도 25만 개로 커져서, 같은 문장을 더 적은 토큰으로 처리합니다. 토큰이 줄면 비용과 지연이 같이 줄어듭니다.

**처리량.** 알리바바 발표 기준으로 32K 문맥에서 Qwen3-Max의 8.6배, 256K에서 19배 디코딩 처리량입니다. Qwen3-235B-A22B와 비교하면 3.5배·7.2배입니다. 활성 17B로 397B급 지식을 낸다는 구조의 효과가 여기서 나옵니다.

대표 점수도 함께 봐 두겠습니다. 모두 제조사 발표값입니다.

| 벤치마크 | 점수 |
| --- | --- |
| MMLU-Pro | 87.8 |
| GPQA | 88.4 |
| LiveCodeBench v6 | 83.6 |
| SWE-bench Verified | 76.4 |
| Terminal Bench 2 | 52.5 |
| MCP-Mark | 46.1 |
| BrowseComp | 69.0~78.6 (검색 전략에 따라) |
| MathVision | 88.6 |

**언제 쓰나.** 대형 에이전트, 복잡한 추론, 코드와 멀티모달을 한 모델로 처리해야 하는 서버 워크로드입니다. 요청이 많고, 문맥이 길고, 도구를 오래 물고 가는 작업입니다. 같은 지식을 dense 397B로 서빙하는 것보다 토큰당 계산이 4.3%라, GPU를 충분히 확보할 수 있다면 처리량당 비용이 크게 내려갑니다.

**주의할 점.** 오픈 웨이트지만 집에서 돌리는 모델은 아닙니다. FP8 가중치만 400GB 안팎이라 서버급 다중 GPU가 필요합니다. 문맥 1M은 YaRN 확장이고, 네이티브는 256K입니다. 그리고 3.5 세대는 `/think`, `/no_think` 같은 프롬프트 수준 스위치를 공식 지원하지 않습니다. 요청 파라미터로 켜고 끕니다.

### Qwen3.8-27B — 책상에 두는 27B

2026년 8월 14일에 공개됐습니다. 3.5 아키텍처를 기반으로 세대 개선을 얹은 dense 모델이고, Apache 2.0입니다.

| 항목 | 값 |
| --- | --- |
| 파라미터 | 27.78B (카드 표기 27B), 전부 활성 |
| 층 | 64층 (GDN 48 + Gated Attention 16) |
| FFN | dense, intermediate 17,408 |
| 문맥 | 262,144 네이티브, YaRN으로 1M |
| 입력 | 텍스트·이미지·비디오 네이티브 |
| 라이선스 | Apache 2.0 |
| 메모리 | 4비트 16~19GB (24GB 카드 1장) |

여기서 짚어 둘 것이 있습니다. 이름은 "27B dense"지만, 어텐션은 3.5의 하이브리드를 그대로 씁니다. Dense라는 말은 **MoE가 아니다**라는 뜻입니다. 토큰마다 다른 expert를 고르지 않고, 모든 토큰이 같은 FFN을 지납니다. 그래서 서빙이 단순하고, 작은 배치에서도 예측 가능합니다. 반면 KV 캐시는 64층 중 16층만 완전 어텐션이라 4분의 1로 줄어 있습니다.

**씽킹 제어가 이 모델의 특징입니다.** 세 가지 손잡이가 있습니다.

- `enable_thinking` — 요청마다 켜고 끕니다. 기본은 켜짐입니다.
- `reasoning_effort` — `low`, `medium`, `xhigh`. 기본값이 `xhigh`입니다.
- `preserve_thinking` — 이전 턴의 추론 블록을 문맥에 남깁니다. 기본 켜짐입니다.

여기에 API 쪽에서는 `thinking_budget`으로 추론 토큰 상한을 걸 수 있습니다. 상한에 닿으면 추론을 멈추고 바로 답합니다.

샘플링 기본값도 모드별로 다릅니다. 씽킹 모드는 temperature 1.0, top-p 0.95, top-k 20. 비씽킹 모드는 temperature 0.7, top-p 0.8, top-k 20, presence penalty 1.5입니다. 씽킹 모드에서 temperature를 낮추면 오히려 반복에 빠지기 쉬우니, 모델 카드의 권장값을 그대로 쓰는 편이 안전합니다.

점수는 이렇습니다. 역시 제조사 발표값입니다.

| 벤치마크 | 점수 |
| --- | --- |
| Terminal Bench 2.1 | 73.0 |
| SWE-bench Pro | 61.7 |
| QwenSWEBench | 79.0 |
| LiveCodeBench v6 | 90.3 |
| GPQA Diamond | 89.2 |
| OSWorld-Verified | 84.3 |
| MathVision (with CI) | 94.6 |
| OmniDocBench 1.5 | 91.1 |

**언제 쓰나.** 로컬이나 사내 단일 GPU에서 실전 코딩·문서·비전 작업을 할 때의 기본값입니다. 데이터가 밖으로 나가면 안 되고, 네트워크 왕복 없이 짧은 지연으로 답해야 하는 작업입니다. 24GB 카드 한 장에서 4비트로 돌아가고, 코딩 에이전트 하네스와 붙이기 쉽게 나온 것도 이 모델의 목적입니다.

**주의할 점.** 기본값이 `xhigh`라서 생각을 지나치게 많이 하는 경향이 있습니다. 간단한 질문에도 추론이 길어지면 지연과 비용이 같이 올라갑니다. 실무에서는 작업 종류별로 `low`나 `medium`을 지정하는 편이 낫습니다. 그리고 24GB에서 128K 문맥은 KV를 q8로 줄여야 겨우 들어갑니다. 262K를 온전히 쓰려면 48GB급이 편합니다.

한 가지 더. 두 모델의 점수를 나란히 놓으면 27B가 커 보이는 항목이 있습니다. 하지만 문제집이 다릅니다. Terminal Bench **2**와 **2.1**, SWE-bench **Verified**와 **Pro**는 같은 시험이 아닙니다. 세대도 2월과 8월로 다릅니다. 숫자를 가로로 비교하려면 같은 벤치마크, 같은 하네스, 같은 문맥 조건이어야 합니다.

### 그 사이와 그 위 — 작은 모델, 그리고 2.4T

두 모델만 있는 것은 아닙니다. 사이와 위에 선택지가 있습니다.

**Qwen3.5 소형(0.8B~9B).** 2026년 3월에 9B, 4B, 2B, 0.8B가 공개됐습니다. 같은 3.5 세대의 멀티모달·문맥 특성을 유지하면서 노트북이나 엣지에서 도는 크기입니다. 분류, 추출, 라우팅, 짧은 요약처럼 "답의 형식이 정해진" 일을 대량으로 처리할 때 씁니다. 큰 모델의 앞단에서 요청을 걸러 주는 용도로도 잘 맞습니다.

**Qwen3.6의 중간 크기.** 35B-A3B와 27B dense가 2026년 4월에 나왔습니다. 활성 3B짜리 MoE라 24GB 카드에서도 4비트로 돌릴 수 있고, 에이전트 코딩에 초점을 맞춘 세대입니다. 지금 27B를 고른다면 3.6과 3.8 사이에서 고르게 됩니다. 3.8이 최신이고, 3.6은 검증된 안정판입니다.

**Qwen3.8-2.4T-A95B.** 2026년 8월 12일에 공개된 Max급 모델입니다. 총 2.4T, 토큰당 95B 활성, 92층입니다. 텍스트 전용이고 씽킹 모드를 끌 수 없습니다. 라이선스가 Apache 2.0이 아니라 Qwen3.8-Max 라이선스입니다. 월 이용자 1억 명 또는 월 매출 2,000만 달러를 넘는 제품은 모델 이름을 UI에 표시해야 하고, 모델 서비스 사업으로 연매출 5,000만 달러를 넘으면 별도 라이선스를 받아야 합니다. "오픈 웨이트"라고 다 같은 조건이 아니라는 좋은 예입니다.

| 모델 | 크기 | 라이선스 | 놓이는 곳 |
| --- | --- | --- | --- |
| Qwen3.5-0.8B~9B | 0.8B~9B dense | Apache 2.0 | 엣지·노트북, 대량 단순 작업 |
| Qwen3.6-35B-A3B | 35B 총 · 3B 활성 | Apache 2.0 | 24~48GB 워크스테이션 |
| Qwen3.8-27B | 27.78B dense | Apache 2.0 | 24GB 단일 GPU |
| Qwen3.5-397B-A17B | 397B 총 · 17B 활성 | Apache 2.0 | 서버 다중 GPU |
| Qwen3.8-2.4T-A95B | 2.4T 총 · 95B 활성 | Qwen3.8-Max | 대규모 추론 클러스터 |

## 생각해 보기: 호출과 씽킹은 실제로 어떻게 오갈까

여기까지 읽으면 다음 질문이 남습니다. "그래서 API를 부를 때 실제로 무엇이 오가고, 씽킹을 켜면 무엇이 달라지나?" 이 글에서는 답을 정하지 않고, 판단에 필요한 재료만 늘어놓겠습니다.

### 호출의 실제 모양

Qwen3.8-27B를 OpenAI 호환 API로 부르는 예입니다.

```python
from openai import OpenAI

client = OpenAI()  # base_url과 api_key는 사용하는 게이트웨이에 맞춥니다

completion = client.chat.completions.create(
    model="Qwen/Qwen3.8-27B",
    messages=[
        {"role": "system", "content": "너는 코드 리뷰어다. 지적은 파일:줄 형식으로만 쓴다."},
        {"role": "user", "content": "이 diff에서 버그를 찾아 줘.\n\n" + diff},
    ],
    extra_body={
        "chat_template_kwargs": {
            "enable_thinking": True,     # 기본값
            "preserve_thinking": True,   # 기본값
        },
    },
    reasoning_effort="medium",           # xhigh · medium · low
    stream=True,
    stream_options={"include_usage": True},
)
```

스트리밍에는 두 종류의 조각이 섞여 옵니다. `reasoning_content`(추론)와 `content`(답)입니다. 화면에 답만 보여주고 싶으면 앞의 것을 버리면 되지만, 버려도 **청구와 지연에서는 빠지지 않습니다.** 추론 토큰도 출력 토큰입니다.

### 비용과 지연은 어디서 늘어나나

토큰을 세 갈래로 나눠 보면 계산이 쉬워집니다.

| 구간 | 무엇을 재나 | 씽킹을 켜면 |
| --- | --- | --- |
| Prefill | 입력 문맥을 한 번에 처리 | 문맥이 길수록 증가 (추론 블록이 남으면 더) |
| Decode | 토큰을 하나씩 생성 | 추론 토큰만큼 선형 증가 |
| 왕복 | 도구 호출 횟수 | 실패·재시도가 줄면 감소 |

핵심은 **decode가 토큰 수에 정비례**한다는 점입니다. 추론을 600토큰 쓰고 답을 200토큰 쓰면, 답만 쓸 때보다 생성 단계가 4배입니다. 반대로 prefill은 프롬프트를 한 번에 병렬로 처리하므로, 문맥이 조금 길어지는 것보다 토큰을 더 뽑는 쪽이 지연에 더 크게 작용하는 경우가 많습니다.

단가는 보통 출력이 입력보다 비쌉니다. 예를 들어 Qwen3.7-Plus의 공개 단가는 100만 토큰당 입력 $0.40, 출력 $1.20입니다. 출력이 3배입니다. 그래서 추론을 길게 쓰는 것이 "입력을 조금 더 넣는 것"보다 비쌉니다.

### preserve_thinking은 왜 기본값이 켜짐인가

멀티턴 에이전트에서는 추론 블록을 매 턴 버리는 것이 낭비입니다. 턴 2에서 턴 1과 같은 판단을 다시 해야 하기 때문입니다. `preserve_thinking`은 이전 assistant 메시지의 추론 블록을 문맥에 남겨, 같은 고민을 반복하지 않게 합니다. Qwen 문서는 KV 캐시 재사용으로 추론 효율도 좋아진다고 설명합니다.

대가는 문맥입니다. 추론 블록이 쌓이면 입력이 길어지고, prefill 비용과 메모리가 올라갑니다. 그래서 판단 기준은 이렇게 됩니다.

- **결정의 근거가 다음 턴에도 필요한 작업** — 에이전트, 디버깅, 여러 단계 편집. 켜 두는 편이 낫습니다.
- **턴마다 독립적인 작업** — 분류, 요약, 단발 질의. 꺼서 문맥을 줄이는 편이 낫습니다.

### 그런데 effort를 낮추면 정말 빨라지나

직관과 어긋나는 지점이 하나 있습니다. Qwen 문서는 이렇게 적습니다. **멀티턴 에이전트에서는 추론 effort를 낮춰도 전체 완료 시간이 항상 줄지는 않는다.** 턴당 응답은 빨라지지만, 분석이 부족해 실패와 재시도가 늘면 총 지연과 토큰 소비가 오히려 커질 수 있다는 것입니다.

이 말은 곧 "effort는 모델의 성능 손잡이가 아니라 작업의 위험 손잡이"라는 뜻입니다. 정답이 하나로 정해진 작업(테스트 통과, 형식 변환)에서는 낮은 effort가 이깁니다. 탐색과 판단이 필요한 작업(버그 원인, 설계 선택)에서는 높은 effort가 총비용을 줄입니다.

### 생각해 볼 다섯 가지

정답을 정해 두기보다, 다음 실습 전에 스스로 답해 볼 질문으로 남기겠습니다.

1. **내 작업 중 "생각이 필요한 것"과 "형식만 맞추면 되는 것"은 각각 무엇인가?** 이 구분이 되면 `enable_thinking`과 `reasoning_effort`를 작업 단위로 정할 수 있습니다. 지금은 전부 기본값으로 보내고 있지는 않은지.
2. **도구 설명은 모델이 도구를 고르는 유일한 근거다.** 이름만 있고 설명이 빈약한 도구를 쓰고 있지는 않은가? "무엇을 하는지"보다 "언제 쓰는지"를 적었는가?
3. **병렬 도구 호출이 안전한 경계는 어디인가?** 읽기끼리는 병렬로 묶어도 되지만, 쓰기·삭제·결제가 섞이면 순차로 돌려야 합니다. 하네스가 이 경계를 강제하고 있는가?
4. **긴 문맥을 실제로 쓰고 있는가, 비용만 내고 있는가?** 256K를 넣을 수 있다는 것과 256K가 필요한 것은 다릅니다. 대부분의 작업은 검색으로 줄이는 편이 싸고 정확합니다.
5. **내 작업에서 27B로 충분한 일과 397B가 필요한 일을 가르는 기준은 무엇인가?** 동시 요청 수, 문맥 길이, 데이터 반출 가능 여부, 지연 허용치. 이 네 가지로 대개 답이 나옵니다.

## 마무리

정리하면 이렇습니다.

- LLM은 다음 토큰의 확률을 계산해 하나를 고르는 함수이고, 답의 길이가 곧 계산 횟수입니다.
- 능력은 pre-training(압축), SFT(형식), RL(추론·정렬)의 세 단계에서 나옵니다.
- 도구 호출은 모델이 고르고 하네스가 실행하는 루프입니다. 모델은 여전히 텍스트만 뱉습니다.
