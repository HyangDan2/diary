DevOps를 처음 배울 때 가장 헷갈리는 것은 도구 목록입니다. Docker, Kubernetes, Terraform, Jenkins, Argo CD, Prometheus. 이름만 스무 개가 넘습니다. 그런데 정작 필요한 질문은 "무엇을 설치할까"가 아니라 **"무엇을 사람 손에서 떼어낼까"** 입니다.

이 글은 그 질문에 순서대로 답합니다. DevOps가 필요해지는 신호를 먼저 구분하고, 파이프라인을 이루는 여섯 칸을 하나씩 열어 본 다음, HD2Lab에서 실제로 돌아가는 파이프라인 네 개를 그대로 적습니다. 마지막에 DORA 지표와 공식 문서 링크를 붙였습니다. 도구를 고르는 일은 그다음입니다.

## 1. DevOps는 도구가 아니라 순서입니다

DevOps를 한 문장으로 줄이면 이렇습니다. **빌드·검사·배포·감시를 사람의 기억이 아니라 코드와 절차에 맡기는 일.** 도구는 그 순서를 구현하는 수단일 뿐입니다.

파이프라인의 기본 순서는 다섯 단계입니다. 코드를 남기고, 검사하고, 같은 방식으로 만들고, 배포하고, 지켜봅니다.

| 단계 | 사람이 하던 일 | 파이프라인이 하는 일 | 남는 판단 |
| --- | --- | --- | --- |
| 기록 | 폴더를 복사해 두기 | 커밋, 브랜치, PR | 무엇을 한 커밋으로 묶을지 |
| 검사 | 눈으로 열어 보기 | 타입 검사, 테스트, 린트 | 실패했을 때 고칠지 되돌릴지 |
| 생성 | 각자 자기 컴퓨터에서 빌드 | 고정된 환경에서 한 번 | 버전 번호, 릴리스 노트 |
| 배포 | FTP, 복사, 수동 업로드 | 같은 절차를 매번 반복 | 언제 배포할지 |
| 감시 | 사용자 연락을 받고 알기 | 헬스체크, 로그, 알림 | 알림이 왔을 때 무엇을 할지 |

표의 오른쪽 칸을 보면 알 수 있습니다. 자동화가 가져가는 것은 **기억**과 **반복**이고, 판단은 남습니다. DevOps를 한다고 판단이 없어지지 않습니다. 오히려 판단할 시간이 생깁니다. "이 명령을 어느 순서로 쳤더라"를 떠올리는 데 쓰던 시간이 "이번 배포를 오늘 할까"를 결정하는 데로 옮겨 갑니다.

## 2. 언제 시작해야 하는가 — 신호 네 가지

DevOps는 규모가 커지면 필요해지는 것이 아니라, **같은 일이 두 번째 반복될 때** 필요해집니다. 현장에서 먼저 보이는 신호는 네 가지입니다.

| 신호 | 실제 모습 | 그대로 두면 |
| --- | --- | --- |
| 수동 빌드·배포의 반복 | 배포 노트에 명령 다섯 줄, 하나 빼먹으면 처음부터, 배포마다 결과가 조금씩 다름 | 배포가 두려워지고, 미뤄지고, 한꺼번에 몰린다 |
| 환경 불일치 | "내 컴퓨터에선 되는데", Node 18과 22, lockfile 없음, OS마다 다른 경로 | 버그가 아니라 환경을 의심하는 시간이 늘고, 재현이 안 되니 고칠 수 없다 |
| 장애를 사용자가 먼저 안다 | 배포 30분 뒤에 온 메시지, 남은 로그 없음, 서버는 살아 있는데 응답이 없음 | 신뢰가 먼저 깎인다. 복구 시간이 곧 평판이 된다 |
| 시크릿이 코드에 섞임 | `.env` 커밋, 소스 안의 토큰, 모든 권한을 가진 배포 키 | 한 번 새면 이력에 남고, 결국 전부 회전해야 한다 |

여기에 해당하는 작은 신호도 있습니다.

- 금요일에는 배포하지 않는다는 말하지 않은 규칙이 있다.
- 배포할 수 있는 사람이 한 명이다. 그 사람이 없으면 아무도 못 한다.
- 롤백이 "이전 커밋을 다시 손으로 빌드하는 일"이다.
- 릴리스마다 체크리스트 문서를 새로 만든다. 그리고 매번 한 항목을 빠뜨린다.

판단은 두 문장이면 됩니다. **같은 일을 두 번째 손으로 반복하고 있는가. 그 일이 실패했을 때 아무도 모르는가.** 둘 중 하나라도 그렇다면 그 자리가 첫 후보입니다.

[![손으로 하는 배포와 파이프라인의 비교: 같은 다섯 단계를 사람이 기억으로 잇는 쪽과 파일로 고정한 쪽](/diary/assets/images/2026-11-23-devops-manual-vs-pipeline.png)](/diary/assets/images/2026-11-23-devops-manual-vs-pipeline.png)

반대쪽도 분명히 해 둡니다. 아직 한 번도 배포하지 않은 프로젝트에 파이프라인을 붙이는 것은 비용만 됩니다. 배포할 것이 생기고, 그 배포가 반복되고, 그 반복이 무서워질 때 시작하면 늦지 않습니다.

## 3. 구성요소 여섯 가지

파이프라인은 여섯 칸으로 이루어집니다. 순서가 있고, 앞의 칸이 무너지면 뒤의 칸이 의미를 잃습니다. 테스트가 없는 자동 배포는 빠른 사고이고, 기록이 없는 테스트는 재현이 안 되는 통과입니다.

[![여섯 칸의 구조: 기록·검사·생성·배포를 가로로 잇고, 시크릿과 관측성이 위아래에서 받치는 모양](/diary/assets/images/2026-11-23-devops-six-parts.png)](/diary/assets/images/2026-11-23-devops-six-parts.png)

### ① 버전 관리와 브랜치 규율

버전 관리의 대상은 코드만이 아닙니다. 워크플로 파일, 배포 설정, 문서, 작은 스크립트까지 같은 이력에 들어갑니다. 그래야 "그때 무엇이 달라져서 이렇게 됐는지"를 나중에 되짚을 수 있습니다.

규율은 세 가지로 충분합니다.

1. **`main`은 언제나 배포 가능한 상태로 둡니다.** 작업은 짧은 브랜치에서 하고 PR로 합칩니다.
2. **커밋은 되돌릴 수 있는 단위로 나눕니다.** 리팩터링과 기능과 포맷팅을 한 커밋에 섞으면 `revert` 한 번으로 되돌릴 수 없습니다.
3. **메시지는 나중의 내가 읽습니다.** `fix(nav): stop the header from covering the first section`처럼 무엇이 왜 바뀌었는지 한 줄에 담습니다.

```bash
git switch -c fix/header-overlap
# 고치고 확인하고
git commit -m "fix(nav): stop the header from covering the first section"
git push -u origin fix/header-overlap
gh pr create --fill
```

혼자 하는 프로젝트에서도 PR을 쓰는 이유는 검토를 받기 위해서가 아니라 **기록을 남기기 위해서**입니다. PR 본문은 나중에 이 변경을 다시 만났을 때 읽을 메모이고, 되돌릴 때의 단위이기도 합니다.

확인은 간단합니다. `main`에서 방금 빌드가 되는가. 지난주 변경을 `revert` 한 번으로 되돌릴 수 있는가.

### ② CI — 자동 검사

CI는 "내가 push하면 누군가 대신 확인해 주는 것"입니다. 그 누군가가 없으면 기계가 합니다. 검사 항목은 프로젝트마다 다르지만 순서는 같습니다. **싼 것부터** 돌립니다.

| 순서 | 검사 | 걸리는 시간 | 실패했을 때 알 수 있는 것 |
| --- | --- | --- | --- |
| 1 | 타입 검사, 린트 | 초 | 문법, 타입, import 오류 |
| 2 | 단위 테스트 | 수십 초 | 계산과 상태 로직의 회귀 |
| 3 | 통합 테스트 | 분 | 경계에서의 불일치 |
| 4 | E2E 테스트 | 수 분 | 실제 브라우저에서의 동작 |

1번이 1분 안에 끝나야 하는 이유는 심리적인 것입니다. 실패를 빨리 알면 고치고, 늦게 알면 그사이 다른 일을 벌입니다.

최소 구현은 워크플로 하나입니다.

```yaml
name: ci
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci          # lockfile 그대로 설치
      - run: npx tsc --noEmit
      - run: npm test
```

`npm ci`를 쓰는 이유는 `npm install`과 다르게 lockfile을 바꾸지 않고 그대로 설치하기 때문입니다. CI에서 lockfile이 조용히 갱신되면 "CI에서만 다르게 동작하는" 상태가 생깁니다.

흔한 실패는 세 가지입니다. CI에서만 실패하는 테스트(시간대, 네트워크, 실행 순서에 의존), 가끔 실패하는 테스트를 넘기다가 **CI 전체를 무시하게 되는 것**, 로컬에서 한 번도 돌려 보지 않고 push하는 것. 세 번째는 CI를 붙인 뒤에도 계속 생깁니다. 규칙 하나로 막습니다. **빨간 CI를 안고 머지하지 않습니다.** 급하면 테스트를 고치거나, 실패를 이슈로 남기고 명시적으로 예외를 둡니다.

### ③ CD — 자동 배포와 롤백

CD의 핵심은 "자동"이 아니라 **"같은 방식으로 매번"** 입니다. 산출물이 한 번 만들어지고, 그 산출물이 그대로 배포됩니다. 로컬에서 다시 빌드한 것을 손으로 올리는 순간, 테스트한 것과 배포한 것이 달라집니다.

배포 방식은 대상에 따라 다릅니다.

| 대상 | 배포 | 무중단 방법 |
| --- | --- | --- |
| 정적 사이트 | 빌드 산출물을 Pages나 CDN에 올림 | 파일 단위 원자적 교체. 사실상 무중단 |
| 컨테이너 서비스 | 이미지를 만들어 레지스트리에 올리고 교체 | 롤링, 블루-그린, 카나리 |
| 서버리스 | 함수와 설정을 배포 | 버전과 별칭(alias)으로 전환 |

롤백은 CD의 절반입니다. 배포는 자동인데 되돌리기가 수동이면 절반만 된 것입니다. 가장 확실한 롤백은 **이전 커밋을 되돌리는 커밋**을 올리고 같은 파이프라인을 다시 태우는 것입니다. 그래서 "배포를 되돌리는 데 몇 분이 걸리는가"가 CD 성숙도를 재는 가장 쉬운 질문입니다.

배포 job은 빌드가 끝난 산출물만 받아야 합니다. GitHub Actions에서는 `needs`와 권한 선언으로 그 경계를 만듭니다.

```yaml
  deploy:
    needs: build                 # 빌드가 실패하면 여기까지 오지 않는다
    permissions:
      contents: read
      pages: write
      id-token: write
    environment:
      name: github-pages
```

### ④ 환경 격리와 선언적 인프라

"내 컴퓨터에선 되는데"는 코드 문제가 아니라 환경 문제입니다. 환경을 말로 설명하는 대신 파일로 적으면, 그 파일이 곧 재현 가능한 환경이 됩니다. 단계를 밟으면 이렇습니다.

1. **버전 고정** — `.nvmrc`, `package.json`의 `engines`, `packageManager`.
2. **lockfile 커밋** — 설치 결과를 고정합니다.
3. **`.env.example`** — 필요한 설정 키를 값 없이 나열합니다.
4. **컨테이너** — `Dockerfile`과 `compose.yaml`로 OS와 런타임까지 고정합니다.
5. **인프라 선언** — 서버, DNS, 스토리지를 코드로 적습니다.

정적 사이트에 Kubernetes는 필요 없습니다. GitHub Pages와 Node 버전 고정으로 충분합니다. 반대로 외부 패키지를 빌드해야 하는 파이프라인이라면 컨테이너가 거의 유일한 답입니다. 도구의 크기는 프로젝트의 크기에 맞춥니다.

선언적이라는 말은 "서버에 들어가 명령하지 않는다"는 뜻입니다. 손으로 한 일은 기록되지 않고, 다음 사람은 그 사실을 모릅니다. 파일에 적고 다시 적용하면, 같은 일을 두 번 설명할 필요가 없습니다.

[Twelve-Factor App](https://www.12factor.net/)의 원칙 중 지금 바로 쓸 수 있는 것은 세 가지입니다. 설정은 코드가 아니라 환경변수로, 개발과 운영 환경은 최대한 같게, 로그는 파일이 아니라 흐르는 스트림으로.

확인은 이렇습니다. 새 노트북에서 저장소를 받아 30분 안에 빌드되는가. 컨테이너가 로컬과 같은 결과를 내는가.

### ⑤ 시크릿과 최소 권한

시크릿은 코드에 넣지 않습니다. 대신 저장소나 배포 플랫폼의 secret store에 둡니다. `.env`는 커밋하지 않고, `.env.example`로 키 목록만 공유합니다.

워크플로의 권한은 더 자주 잊힙니다. GitHub Actions의 `GITHUB_TOKEN`은 워크플로 파일에 적힌 `permissions`만큼만 힘을 가집니다. 아무것도 적지 않으면 저장소 설정의 기본값을 따르는데, 그 기본값이 넓은 경우가 많습니다. 필요한 것만 적는 편이 안전합니다.

```yaml
permissions:
  contents: read    # 읽기만
  pages: write      # 배포 job에만
  id-token: write   # OIDC로 Pages에 인증
```

배포용 토큰은 저장소 하나에만, 만료일을 두고, 주기적으로 회전합니다. 이미 커밋된 토큰은 이력에서 지워도 안전해지지 않습니다. 지우지 않은 곳에서 여전히 읽히고, 포크와 캐시에 남습니다. **회전이 유일한 답**이고, 이력 재작성은 협업 저장소에서는 더 위험한 선택입니다.

가장 빠른 점검은 질문 하나입니다. **이 저장소를 public으로 바꿔도 문제가 없는가.** 답이 "아니오"라면 무엇이 문제인지가 곧 할 일 목록입니다.

### ⑥ 관측성과 모니터링

배포는 끝이 아니라 시작입니다. "지금 서비스가 정상인가"에 30초 안에 답할 수 있어야 합니다. 그 답을 주는 것이 헬스체크입니다.

헬스체크는 프로세스가 살아 있는지를 보는 것이 아니라 **일을 할 수 있는지**를 봅니다. 데이터베이스에 붙는지, 필수 의존 서비스가 응답하는지, 큐가 밀리지 않았는지. `200 OK`만 돌려주는 엔드포인트는 프로세스가 떠 있다는 것 말고는 알려 주지 않습니다.

알림은 **상태가 바뀔 때만** 보냅니다. 같은 알림이 하루에 열 번 오면 그 알림은 없는 것과 같아집니다. 열 번을 받아 본 사람은 다음부터 알림을 읽지 않고 지웁니다. 알림의 가치는 빈도가 아니라 정확도입니다.

로그는 남기되 읽을 수 있어야 합니다. 요청 ID, 상태 코드, 걸린 시간, 실패한 의존성. 이 네 가지가 한 줄에 있으면 대부분의 장애는 로그만으로 좁혀집니다.

마지막 질문입니다. 새벽 3시에 장애가 나면 누가, 무엇을 보고 아는가. 답이 "아무도 모른다"라면 여섯 번째 칸이 비어 있는 것입니다.

### 여섯 칸 요약

| 칸 | 없을 때 | 최소 | 충분 |
| --- | --- | --- | --- |
| 기록 | 되돌릴 수 없음 | `main` + 짧은 브랜치 | PR + 태그 + 릴리스 노트 |
| CI | 회귀를 사용자가 발견 | 타입 + 단위 테스트 | + E2E, 린트, 번들 크기 |
| CD | 손 배포, 매번 다름 | 빌드 → Pages | 무중단 + 한 번에 롤백 |
| 환경 | 재현 불가 | 버전 고정 + lockfile | 컨테이너 + 선언적 인프라 |
| 시크릿 | 유출 위험 | secrets + `permissions` | 회전 + 자동 스캔 |
| 관측 | 장애를 사용자가 알림 | 헬스체크 + 알림 | 지표 + 로그 + 대시보드 |

### 4-1. Web-HQ 스냅샷 — 자동화가 자동화를 깨우지 않게

Web-HQ 첫 화면의 "최근 업데이트" 목록을 하루 한 번 다시 만드는 워크플로입니다. 지난 28일의 공개 커밋 활동과 저장소별 최신 커밋을 모아 JSON 하나로 떨어뜨립니다. push만으로는 부족합니다. 코드가 그대로여도 다른 저장소에 커밋이 생기면 목록이 낡기 때문에, 매일 정해진 시각에 한 번 더 돌립니다.

```yaml
name: Refresh latest updates

on:
  push:
    branches: [main]
    paths-ignore:
      - "data/latest-updates.json"   # 자기 출력이 자기 트리거가 되지 않게
  schedule:
    - cron: "20 15 * * *"            # 00:20 Asia/Seoul (cron은 UTC)
  workflow_dispatch:

permissions:
  contents: write                    # 스냅샷을 커밋해야 하므로

concurrency:
  group: latest-updates
  cancel-in-progress: false          # 중간에 끊으면 반쯤 쓴 파일이 남는다

jobs:
  snapshot:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "20"
      - run: node tools/build-latest-updates.mjs
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
      - name: Commit when the snapshot changed
        run: |
          if git diff --quiet -- data/latest-updates.json; then
            echo "Snapshot already current."
            exit 0
          fi
          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git add data/latest-updates.json
          git commit -m "chore(data): refresh the latest updates snapshot"
          git push
```

세 가지 장치가 들어 있습니다.

- **`paths-ignore`** — 자기 출력 파일만 바뀐 push는 워크플로를 다시 깨우지 않습니다. `GITHUB_TOKEN`으로 만든 푸시는 원칙적으로 새 실행을 트리거하지 않지만, 토큰이 바뀌거나 다른 자동화가 같은 파일을 건드리면 조건이 달라집니다. 의도를 파일에 적어 두는 편이 안전합니다.
- **`concurrency`** — 같은 그룹은 겹쳐 돌지 않습니다. `cancel-in-progress: false`인 이유는 중간에 끊으면 반쯤 쓴 스냅샷이 남기 때문입니다. 겹치지 않게 하되, 끝까지 돌게 합니다.
- **diff 검사** — 바뀐 것이 없으면 커밋하지 않습니다. 빈 커밋은 이력만 늘리고, 다음 트리거의 원인이 됩니다.

`cron`은 UTC로 읽힙니다. `20 15 * * *`는 한국 시간 00:20입니다. 주석을 남기지 않으면 6개월 뒤에 보는 사람이 반드시 한 번 계산해 봐야 합니다.

여기서 얻은 규칙은 하나입니다. **자동화의 종료 조건을 설계하지 않으면 자동화가 자동화를 부릅니다.** 자기가 만든 파일을 자기가 다시 읽는 구조라면, "바뀌었을 때만"이라는 조건이 반드시 있어야 합니다.

### 4-2. PKPilot과 ADOP0001 — 타입 → 단위 → E2E → Pages

정적 웹앱들은 GitHub Pages에 올라갑니다. 서버가 없으니 CD는 단순하지만, 게이트는 오히려 분명합니다. 테스트를 통과하지 못한 산출물은 Pages에 도달할 경로가 없습니다.

```yaml
name: Deploy to GitHub Pages

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: true      # 새 배포가 오면 이전 배포를 접는다

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npx tsc --noEmit   # 1. 타입
      - run: npm test           # 2. 단위 (Vitest)
      - run: npm run build      # 3. 산출물
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with:
          path: dist

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4
```

게이트는 `tsc` → Vitest → Playwright → Pages 순서입니다. 여기서 Playwright는 CI가 아니라 **머지 전 로컬 게이트**입니다. 브라우저를 설치하고 실제 화면을 띄우는 검사는 분 단위로 비싸서, `npm run test:e2e`로 머지 전에 한 번 돌리고 CI에서는 타입과 단위로 회귀를 막습니다.

이 선택에는 조건이 붙습니다. 팀이 커지거나 릴리스가 잦아지면 E2E도 CI로 옮기는 편이 낫습니다. 대신 그때는 샤딩, 실패 시 스크린샷과 trace 아티팩트, 재시도 정책을 함께 준비해야 합니다. 준비 없이 E2E만 CI에 넣으면 느리고 가끔 실패하는 job이 하나 늘어날 뿐입니다.

저장소마다 스크립트 구성이 조금 다르니, 게이트가 어디에 있는지 먼저 확인하는 편이 좋습니다.

| 저장소 | `build` 스크립트 | CI에서 타입 검사 |
| --- | --- | --- |
| PKPilot0013 (CodePlayground) | `tsc --noEmit && vite build` | build 안에 포함. 그래도 CI에 `npm test`는 따로 |
| 青松館 (ADOP0001) | `tsc --noEmit && vite build` | 워크플로에 `npx tsc --noEmit`을 한 번 더 명시 |
| PKPilot0018 (Sigrún) | `vite build` | build에 없으므로 `typecheck` 스크립트를 따로 |

`build`에 타입 검사가 들어 있으면 CI에서 빠뜨릴 일이 없습니다. 반대로 `vite build`만 있는 저장소는 타입 검사가 조용히 빠질 수 있습니다. "테스트는 통과했는데 배포된 코드에 타입 오류가 있다"는 상황은 대개 이 구멍에서 나옵니다.

`concurrency`의 `cancel-in-progress: true`도 의도가 있습니다. 사이트는 마지막 커밋이 이기는 것이 맞습니다. 이전 배포를 끝까지 돌려 놓으면 더 오래된 산출물이 나중에 올라갈 수 있습니다.

### 4-3. Sigrún(PKPilot0018) — 다른 언어로 짠 참조 구현과 비교

Sigrún은 통계 계산을 하는 앱입니다. 이 앱에는 일반적인 단위 테스트로 잡기 어려운 위험이 있습니다. **기대값을 손으로 적으면, 그 기대값이 틀릴 수 있습니다.** 테스트는 통과하는데 결과가 틀리는 상태가 가능합니다.

그래서 검사를 두 겹으로 만들었습니다. 같은 요청을 두 엔진에 넣고 결과를 비교합니다.

| 역할 | 구현 | 고정 방식 |
| --- | --- | --- |
| 참조 엔진 | Python (numpy, scipy, statsmodels, pandas) | `requirements.txt`로 버전 고정 |
| 검증 대상 | 앱에 실제로 들어간 TypeScript 엔진 | 앱 소스를 그대로 빌드해 사용 |
| 비교 | 케이스별 PASS / FAIL / ERROR 리포트 | FAIL 또는 ERROR가 하나라도 있으면 실패 |

참조 구현을 일부러 다른 언어로 만든 이유는 분명합니다. 같은 언어, 같은 라이브러리로 검증 도구를 만들면 검증 대상과 **같은 실수를 공유**합니다. 둘 다 틀린 값이 나오면 비교는 통과합니다. 스택이 다르면 그런 식으로 같이 틀리는 일이 훨씬 어렵습니다.

CI는 PR마다, `main`에 push할 때마다 돕니다. 골든 데이터셋을 다시 만들었을 때 커밋된 파일과 다르면 그것도 실패입니다. 계산이 결정적인지까지 검사하는 셈입니다. 리포트는 HTML과 JSON으로 아티팩트에 30일 남깁니다. 실패했을 때 "어느 케이스가 얼마나 틀렸는지"가 남아야 다음 수정이 한 번에 끝납니다.

이 워크플로는 **아무것도 배포하지 않습니다.** 같은 저장소의 `deploy.yml`은 Pages에 올리고, `qa-stats.yml`은 검사만 합니다. 두 job의 권한도 다릅니다. 검사 job에 `pages: write`가 없는 것은 의도입니다.

### 4-4. 개인 서버 — 10분마다, 상태가 바뀔 때만

마지막은 서버 감시입니다. 개인 서버의 상태 페이지가 `/api/status`에 지금 상태를 JSON으로 내려줍니다.

```json
{
  "mode": "normal",
  "title": "자기야, 서버는 정상 운영 중이야 💜",
  "body": "연결 신호가 잘 들어오고 있어. 안심하고 이용해 줘!",
  "last_signal": "2026-11-23T03:13:24+00:00",
  "updated_at": "2026-11-23T03:13:40+00:00"
}
```

감시자는 10분마다 이 주소를 부릅니다. 절차는 다섯 단계입니다.

1. 요청을 보내고 200 응답과 `mode` 값을 확인합니다.
2. 실패하면 2초 뒤에 한 번 더 확인합니다.
3. 지난번 상태와 비교합니다.
4. 상태가 바뀌었으면 상태 파일에 기록하고 알립니다.
5. 바뀌지 않았으면 아무 말도 하지 않습니다.

| 이벤트 | 조건 | 알림 |
| --- | --- | --- |
| `down` | 연결 실패, 200이 아님, JSON이 깨짐 (두 번 연속) | 서버 응답 없음. 마지막 신호 시각과 함께 |
| `outage` | `mode`가 `outage` | 장애. API가 내려준 제목과 본문 |
| `maintenance` | `mode`가 `maintenance` | 점검 전환 |
| `recovered` | 정상이 아닌 상태에서 `normal`로 복귀 | 복구. 장애가 얼마나 이어졌는지 |
| 변화 없음 | 위에 해당하지 않음 | 알리지 않음 |

두 번 확인하는 이유는 오탐입니다. 새벽에 한 번 튄 네트워크 오류로 사람을 깨우면, 그 알림은 다음부터 신뢰를 잃습니다. 2초를 더 쓰는 것이 낫습니다.

상태를 서버가 아니라 **감시자 쪽 파일에** 저장하는 것도 의도입니다. "지난번에 정상이었는지"를 모르면 전이를 알 수 없고, 전이를 모르면 매번 알리거나 아무것도 알리지 못합니다. 알림 문구를 API가 내려주는 것도 같은 이유입니다. 문구를 한 곳에서 고치면 감시자는 그대로 따라갑니다.

## 5. 더 알아볼 것

### DORA 지표 — 배포가 건강한지 재는 숫자

DORA는 소프트웨어 전달 성능을 재는 연구 프로그램이고, 오랫동안 네 가지 지표로 알려져 있었습니다. 지금은 다섯 개로 정리되어 있습니다.

| 지표 | 무엇을 재는가 | 좋아지는 방향 | 혼자 개발할 때 재는 법 |
| --- | --- | --- | --- |
| 배포 빈도 (Deployment Frequency) | 일정 기간에 배포한 횟수 | 잦을수록 좋음 | 이번 달 배포한 날 수 |
| 변경 리드타임 (Change Lead Time) | 커밋에서 운영 반영까지 걸린 시간 | 짧을수록 좋음 | 머지 시각과 배포 시각의 차이 |
| 변경 실패율 (Change Fail Rate) | 배포 뒤 즉시 손봐야 했던 비율 | 낮을수록 좋음 | 롤백·핫픽스 비율 |
| 배포 실패 복구 시간 (Failed Deployment Recovery Time) | 실패한 배포에서 복구까지 걸린 시간 | 짧을수록 좋음 | 되돌리는 데 걸린 시간 |
| 배포 재작업률 (Deployment Rework Rate) | 장애 때문에 계획 없이 한 배포의 비율 | 낮을수록 좋음 | 급하게 올린 배포의 비율 |

예전에는 복구 시간을 MTTR(평균 복구 시간)이나 "서비스 복구 시간"으로 불렀습니다. 지금 이름이 "배포 실패 복구 시간"으로 바뀐 것은 무엇을 재는지 분명히 하기 위해서입니다. 장애의 원인이 배포인지 아닌지에 따라 재는 대상이 달라지기 때문입니다.

이 지표들이 유용한 이유는 **서로를 견제**하기 때문입니다. 배포 빈도만 올리면 실패율이 오르고, 실패율만 낮추려면 배포를 안 하게 됩니다. 좋은 팀은 속도와 안정성을 맞바꾸지 않는다는 것이 DORA 연구의 오래된 결론입니다.

주의할 점도 있습니다. 지표를 목표로 삼으면 지표를 위한 행동이 나옵니다. "이번 달 배포 30회"를 목표로 잡으면 의미 없는 배포가 30번 생깁니다. 숫자는 추세를 보고 병목을 찾는 데만 씁니다.

### 블루-그린과 카나리

무중단 배포의 대표적인 두 방식입니다.

| 방식 | 원리 | 비용 | 어울리는 곳 |
| --- | --- | --- | --- |
| 롤링 | 인스턴스를 하나씩 새 버전으로 교체 | 낮음 | 일반적인 웹 서비스 |
| 블루-그린 | 두 벌을 나란히 두고 트래픽을 한 번에 전환 | 두 배의 자원 | 롤백이 빨라야 하는 서비스 |
| 카나리 | 일부 사용자에게만 먼저 보내고 지표를 보고 확대 | 낮음, 운영 부담 있음 | 위험이 큰 변경, 트래픽이 많은 서비스 |

정적 사이트에는 해당하지 않습니다. 파일을 통째로 교체하는 배포는 이미 원자적이고, 실패하면 이전 커밋을 다시 올리면 됩니다. 이 표가 필요해지는 시점은 서버나 API를 직접 운영할 때입니다.

### Shift-Left 보안

보안 검사를 배포 뒤가 아니라 **커밋 쪽으로 당기는** 일입니다. 왼쪽으로 당길수록 고치는 비용이 싸집니다.

| 시점 | 검사 | 도구 |
| --- | --- | --- |
| 커밋 전 | 비밀번호·토큰이 들어갔는지 | `.gitignore`, pre-commit hook |
| PR | 의존성 취소, 코드 스캔, 권한 검토 | Dependabot, CodeQL, `permissions` |
| 빌드 | 재현 가능한 빌드, 아티팩트 서명 | lockfile, OIDC, SBOM |
| 배포 후 | 이상 행동 탐지 | 로그, 알림 |

보안 사고의 절반은 "권한이 필요 이상으로 넓었다"에서 옵니다. 코드를 잘 짜는 것보다 토큰의 범위를 좁히는 일이 먼저일 때가 많습니다.

### HD2Lab에서 다음에 붙일 것

- 배포 후 스모크 테스트를 워크플로 마지막 단계로 넣기. 지금은 배포 성공까지만 확인합니다.
- Lighthouse 성능 예산. 번들 크기가 조금씩 늘어나는 것을 사람이 알아채기 어렵습니다.
- 오래된 저장소의 워크플로 권한 일괄 점검. 초기에 만든 워크플로일수록 `permissions`가 비어 있습니다.
- 알림 채널 정리. 지금은 서버 상태 변화만 오도록 되어 있고, 이 정도가 적당합니다.

## 마무리

DevOps는 설치하는 것이 아니라 **순서를 정하는 일**입니다. 도구는 그 순서를 굳히는 수단이고, 순서가 없는 도구는 관리할 것이 하나 더 늘어난 것과 같습니다.

오늘 할 수 있는 가장 작은 첫걸음은 세 가지입니다.

1. push할 때 타입 검사와 단위 테스트가 도는 워크플로 하나를 붙입니다.
2. 배포 절차를 README에 적고, 그대로 스크립트로 옮깁니다. 다음 배포는 그 스크립트만 실행합니다.
3. 지금 상태를 돌려주는 주소 하나를 만듭니다. `/api/status`나 `/healthz`면 충분합니다.

세 가지를 하고 나면 다음에 무엇을 붙일지가 저절로 보입니다. 배포가 무서우면 롤백을, 장애를 사용자가 알려 주면 감시를, 환경이 자꾸 달라지면 컨테이너를 붙이게 됩니다. 순서를 한 번 세워 두면, 도구는 그때그때 골라 쓰면 됩니다.
